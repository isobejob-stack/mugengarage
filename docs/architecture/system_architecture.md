# system_architecture.md — システム全体構成

## 1. Purpose（目的）

本ドキュメントは、M-GARAGE Platformの全体構成（何が・どこで・どう動くか）を定義する。技術選定の理由は `docs/decisions/adr-001-tech-stack.md` を参照。ここでは採用技術を前提に、システム全体の構成・デプロイの流れ・データの流れを定義する。

## 2. Scope（対象範囲）

インフラ構成、デプロイフロー、主要コンポーネント間の関係を対象とする。各ドメイン（在庫・CRM等）の詳細なDB設計・API設計は `docs/database/`・`docs/api/` で個別に定義する。

## 3. 全体構成図（テキスト表現）

```
[運用者（55歳・非エンジニア）]
        │ スマホ／PCブラウザで操作
        ▼
[管理画面（Admin UI）] ── 認証必須
        │
        │  同一Next.jsアプリ内
        ▼
┌─────────────────────────────┐
│   Next.js アプリケーション    │
│  ・公開サイト（Public Website） │
│  ・管理画面（Admin UI）        │
└─────────────────────────────┘
        │              │
        │ データ読み書き │ 画像・動画アップロード
        ▼              ▼
  [Supabase]       [Supabase Storage]
  （PostgreSQL）      （メディアファイル）
        ▲
        │ コード変更をpush
[GitHub リポジトリ]
        │ 自動検知・自動ビルド・自動公開
        ▼
   [Vercel]（ホスティング）
        │
        ▼
[一般ユーザー（サイト閲覧者）]
```

## 4. 主要コンポーネント

### 4.1 Public Website（公開サイト）

- 一般ユーザーがブラウザからアクセスする、車両一覧・車両詳細・図鑑・年表・ライブラリ・ブログ・整備実績等の公開ページ
- Next.jsのSSR/SSGにより高速表示・SEO最適化を行う
- LINE相談CTA、お気に入り、検索機能を含む

### 4.2 Admin UI（管理画面）

- 運用者（エムガレージ店主）が車両登録・記事投稿・顧客管理・問い合わせ対応等を行う画面
- Public Websiteと同一のNext.jsアプリケーション内に、認証必須の管理者専用領域として構築する（インフラを分けない。運用・デプロイの単純化のため）
- スマホでの操作を前提としたUI（00_project.md 8章、03_non_functional_requirements.md 8章）

### 4.3 Database（Supabase / PostgreSQL）

- 車両・顧客・問い合わせ・記事・図鑑・年表・ライブラリ・整備実績・価格履歴・監査ログ等、すべての構造化データを保持する
- ドメインごとのテーブル設計は `docs/database/` で定義する

### 4.4 Storage（Supabase Storage）

- 車両写真（1台あたり実質50枚程度）、記事の挿入画像等を保管する
- 動画は外部（YouTube等）のURLをDBに保持する方式とし、動画ファイル自体はアップロードしない（BR-DATA-001, FR-INV-010に整合）

### 4.5 認証（Auth）

- Supabase Authを用いて、管理画面へのアクセスを認証必須にする（03_non_functional_requirements.md 9章）
- 一般ユーザー向けの会員登録機能は初期リリースでは不要（お気に入りの保存方式は database/ で別途定義する）

## 5. デプロイフロー（公開の仕組み）

1. Claude Codeがコードを実装し、GitHubリポジトリに変更を記録（push）する
2. Vercelがリポジトリの変更を自動検知する
3. Vercelが自動でビルド（サイトの組み立て）を行う
4. ビルドが成功すると、自動的に本番サイトへ反映される
5. 運用者は上記の技術的な工程を一切意識する必要がない。日常運用（車両登録・記事投稿等）はAdmin UIからの操作のみで完結し、コードの変更・デプロイは発生しない

## 6. データの流れ（例：車両を1台登録する場合）

1. 運用者がAdmin UIから車両情報・写真を入力する
2. 車両情報（テキストデータ）はSupabase（PostgreSQL）に保存される
3. 写真はSupabase Storageにアップロードされ、そのURLが車両データに紐付けられる
4. 公開ステータスを「公開」にすると、Public Websiteの一覧・詳細ページ・検索結果に即座に反映される
5. 価格を変更した場合、変更前価格と変更日時が自動的に価格履歴テーブルに記録される（BR-HIST-001）

## 7. 非機能要件との対応

| 非機能要件（03章）               | 本構成での対応                                                                                             |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| サーバー管理コスト最小化（11章） | サーバーレス構成（Vercel + Supabase）のためサーバー管理作業がゼロ                                          |
| ノーコード運用（11章）           | 運用者はAdmin UIのみを操作し、コード変更は行わない                                                         |
| SEO要件（7章）                   | Next.jsのSSR/SSGでメタ情報・構造化データを動的生成                                                         |
| 可用性（5章）                    | Vercel・Supabaseのマネージドインフラの標準SLAに準拠                                                        |
| データ保全（10章）               | Supabase（PostgreSQL）の自動バックアップ機能を利用。論理削除・価格履歴・監査ログはアプリケーション側で実装 |
| 長期運用・ロックイン回避（12章） | Next.js／PostgreSQLは標準的な技術のため、将来的な移行が可能（詳細はADR-001参照）                           |

## 8. 将来の拡張性

- CSV連携・外部API連携（グーネット等）は、Supabase上のデータ構造を疎結合に保つことで、将来的にAPI層を追加するだけで対応可能とする（01_business_requirements.md 8章、BR-SCOPE-001）
- LINE API連携についても、現状は「公式LINEへの遷移リンク」のみとし、将来的な自動応答等の拡張時にAPI連携を追加できる設計とする
