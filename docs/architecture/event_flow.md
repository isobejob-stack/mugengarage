# event\_flow.md — イベントフロー

## 1\. Purpose（目的）

システム内で発生する主要な「出来事（イベント）」が、どの順序で・何を連動して発生させるかを整理する。bounded\_context.mdで定義したコンテキスト間の連携が、実際の業務操作の中でどう動くかを具体化し、次工程（database/・api/）でのトランザクション設計・API設計の土台とする。

## 2\. Scope（対象範囲）

02\_functional\_requirements.md の主要機能のうち、複数エンティティ・複数コンテキストにまたがる代表的な業務イベントを対象とする。単純なCRUD（例：単一記事の編集）は対象外とする。

## 3\. イベントフロー一覧

### 3.1 車両を新規登録し公開する

| #   | 出来事                                                                 | 連動して発生すること                                                                                   |
| --- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1   | 運用者がAdmin UIで車両情報を入力する（メーカー〜グレードを選択）       | Grade選択によりGradeTemplateから初期値（エンジン説明・故障事例・維持費）が自動入力される（FR-VEH-004） |
| 2   | 運用者が自由入力項目を編集し、写真をアップロードする                   | VehiclePhotoレコードが作成される                                                                       |
| 3   | 運用者がSEO項目・タグを設定する                                        | SEOMetaレコード（対象種別：Vehicle）とタグ紐付けが作成される                                           |
| 4   | 運用者が関連図鑑・関連記事を紐付ける                                   | RelatedContentレコードが作成される（参照のみ、コピーしない）                                           |
| 5   | 運用者が公開ステータスを「公開」に変更する（または公開予約を設定する） | Vehicleのステータスが更新される。即時公開の場合はPublic Websiteの一覧・検索・詳細ページに反映される    |
| 6   | 上記すべての変更操作                                                   | AuditLogに変更内容が記録される（BR-HIST-002）                                                          |

### 3.2 価格を変更する

| #   | 出来事                          | 連動して発生すること                                                                                    |
| --- | ------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1   | 運用者がVehicleの価格を変更する | 変更前価格・変更後価格・変更日時を持つPriceHistoryレコードが**追加**される（上書きしない、BR-HIST-001） |
| 2   | Vehicleの価格が更新される       | Public Websiteの車両詳細ページ・検索結果に新価格が反映される                                            |
| 3   | 上記の変更操作                  | AuditLogに記録される                                                                                    |

### 3.3 車両が売約済になる

| #   | 出来事                                                                 | 連動して発生すること                                                             |
| --- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1   | 運用者がVehicleのステータスを「売約済」に変更する                      | Vehicleは削除されず、ステータスのみ変更される（BR-DEL-003）                      |
| 2   | ステータスが「売約済」になったことを検知                               | Public Websiteの在庫一覧・検索結果からは除外される（非公開の在庫として扱われる） |
| 3   | 運用者がオーナーズアーカイブ情報（レストア履歴・販売履歴等）を追加する | OwnerArchiveEntryレコードがVehicleに紐づけて作成される                           |
| 4   | アーカイブ情報が公開される                                             | Public Websiteのオーナーズアーカイブ一覧・詳細ページに表示される（FR-OWN-003）   |

### 3.4 一般ユーザーが車両にお気に入り登録する

| #   | 出来事                                         | 連動して発生すること                                                                                              |
| --- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 1   | ユーザーが車両詳細ページで「お気に入り」を押す | Favoriteレコードが作成される（ユーザー識別子とVehicle IDの紐付け）                                                |
| 2   | Favoriteレコードが蓄積される                   | 管理画面でお気に入り分析（FR-FAV-003）・人気ランキング（FR-FAV-004）に反映される                                  |
| 3   | ユーザーが問い合わせ時に連絡先を残した場合     | Customer（CRM）とFavoriteが紐付けられ、管理画面から「この顧客が気になっている車両」として確認できる（FR-CRM-005） |

### 3.5 問い合わせが発生する

| #   | 出来事                                                                                         | 連動して発生すること                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 1   | ユーザーが問い合わせフォームを送信する（または電話・LINE等で連絡が入り、運用者が手動記録する） | Inquiryレコードが作成される。チャネル・分類（購入/修理/売却/部品/その他）が記録される                                  |
| 2   | Inquiryが作成される                                                                            | 既存Customerと紐付けるか、新規Customerが作成される（FR-INQ-003）                                                       |
| 3   | 運用者が対応する                                                                               | Inquiryの対応ステータス（未対応／対応中／完了）が更新される。CustomerのタイムラインにInquiryが表示される（FR-CRM-002） |
| 4   | 対応後、必要に応じて                                                                           | Reminder（例：車検時期の連絡）が設定される                                                                             |

### 3.6 図鑑・年表・ライブラリ項目を単体で公開する（在庫非依存）

| #   | 出来事                                            | 連動して発生すること                                                                                     |
| --- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1   | 運用者がEncyclopediaEntry（図鑑項目）を作成する   | 対応するVehicleが存在するか否かに関わらず作成・公開できる（BR-DOM-001）                                  |
| 2   | 該当する在庫車両が存在する場合                    | 図鑑ページに関連在庫車両が自動表示される（FR-ENC-005）。存在しない場合は何も表示せず、エラーにもならない |
| 3   | TimelineEvent（年表イベント）を作成する場合も同様 | 特定の車両インスタンスには紐付けず、図鑑項目・記事への紐付けのみ可能とする（BR-DOM-003）                 |

### 3.7 URLを変更する（Slug変更）

| #   | 出来事                                                   | 連動して発生すること                                                        |
| --- | -------------------------------------------------------- | --------------------------------------------------------------------------- |
| 1   | 運用者がコンテンツ（車両／記事／図鑑等）のSlugを変更する | 旧SlugをキーとするRedirect（301）レコードが自動的に作成される（BR-URL-002） |
| 2   | 一般ユーザーが旧URLにアクセスする                        | Redirectテーブルが参照され、新URLへ301リダイレクトされる                    |
| 3   | サイトマップ生成タイミング                               | 新Slugが反映されたサイトマップが再生成される（FR-SEO-005）                  |

## 4\. トランザクション上の注意点（次工程への申し送り）

- 3.1・3.2・3.3のように「主エンティティの更新＋履歴／ログの追加」が同時に発生する処理は、**両方成功するか両方失敗するか**を保証する必要がある（片方だけ成功する状態を作らない）。database/・api/ フェーズで具体的な実装方針を定義する
- 3.7のSlug変更とRedirect作成は、同一操作内で必ずセットで発生させる（Redirect作成を運用者の手動操作に依存させない）

## 5\. Acceptance Criteria（本ドキュメントの受け入れ基準）

- \[ ] 主要な業務イベント（3.1〜3.7）が、bounded\_context.mdのコンテキスト間連携ルールに矛盾なく整理されている
- \[ ] 04\_business\_rules.mdの主要ルール（BR-HIST-001, BR-DEL-003, BR-DOM-001/003, BR-URL-002）が、対応するイベントフローの中で具体的に担保されている
- \[ ] トランザクション上の注意点（4章）が、次工程（database/・api/）で見落とされないよう明記されている
