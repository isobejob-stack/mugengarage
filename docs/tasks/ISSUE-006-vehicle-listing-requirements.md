# ISSUE-006 車両掲載情報の要件定義（再定義）

## 起票日

2026-08-13

## 背景

発注者より「一般的な車検索サイト（車選びドットコム、カーセンサー、グーネット）で
掲載されている車の情報の網羅性が担保できていない」との指摘。
あわせて「ユーザーは使い慣れた操作感を良いUXと考えがち」「年齢層が高い顧客も多い」ため、
**既存サービスのUIUXを参考にする**方針が示された。

本ドキュメントは、車両掲載情報を要件レベルから定義し直すもの。

## 根拠とした情報

開発環境からは3サイトへの通信が遮断されている（`EGRESS_BLOCKED`）ため、
サイトを直接参照して項目を数えることはできていない。代わりに以下を根拠とする。

1. **発注者から共有されたグーネットの実掲載データ15台分**（一次情報。これが最も確度が高い）
2. 中古車情報サイトで一般的に掲載される項目に関する一般知識

グーネット掲載データに実際に含まれていた項目は以下（欠落の判定はここを基準にする）。

```
支払総額 / 車両本体価格 / 諸費用 / 法定整備 / 保証（期間・距離）
年式 / 走行 / 車検 / 排気量 / 修復 / 地域
```

## 2. 提案するデータ項目定義

### 2.1 車検の状態（最優先）

日付1本では表現できないため、状態と日付を分ける。

```
shaken_status : enum('inspection_included', 'valid_until', 'none', 'unknown')
                車検整備付 / 満了日あり / 車検なし / 不明
shaken_expiry : date   （shaken_status = 'valid_until' のときのみ使用。既存カラムを流用）
```

表示ルール:
- `inspection_included` → 「車検整備付」
- `valid_until` → 「2027年2月まで」（日が不明な場合は年月のみ表示）
- `none` → 「車検なし」
- `unknown` → 表示しない

> 満了"日"が分からないケースが実際に多いため、**年月だけでも表示できる**必要がある。
> 日付を推測で埋めると購入判断に関わる情報を誤って出すことになるため避ける。

### 2.2 取引条件

```
legal_maintenance : enum('included', 'separate', 'none')  法定整備（整備付/別途/なし）
warranty_type     : enum('with', 'without')               保証の有無
warranty_months   : integer                                保証期間（月）
warranty_km       : integer                                保証距離（km）
recycle_fee       : enum('included', 'separate', 'none')   リサイクル料金
```

### 2.3 車両基本情報の追加

```
steering_side  : enum('right', 'left')     ハンドル位置
fuel_type      : text                       燃料
capacity       : integer                    乗車定員
door_count     : integer                    ドア数
has_record_book: boolean                    記録簿
is_non_smoking : boolean                    禁煙車
model_code     : text                       車両型式
location_text  : text                       所在地（店舗設定から既定値を引く）
```

### 2.4 装備品

装備は項目数が多く、今後増減する。車両ごとに列を増やす設計は破綻するため、
**マスタ＋中間テーブル**とする（タグ機能と同じ考え方 / BR-DATA-003）。

```
equipments          : id, name, category, display_order
vehicle_equipments  : vehicle_id, equipment_id
```

初期マスタ案（カテゴリ別）:
- 快適装備: エアコン, パワーステアリング, パワーウィンドウ, キーレス, クルーズコントロール
- 内装: 革シート, パワーシート, シートヒーター, ウッドパネル
- 外装: サンルーフ, アルミホイール, フォグランプ
- オーディオ・ナビ: 純正オーディオ, ナビ, ETC, バックカメラ
- 安全装備: ABS, エアバッグ, 盗難防止装置

> クラシックJaguar固有の装備（ウッドパネル等）を入れられる点が、汎用サイトに対する差別化になる。

## 3. 画面要件

### 3.1 一覧カード（現状は情報が不足）

**現状**: 写真 / 車名 / 年式 / 価格 のみ。

**3サイト共通の掲載項目**に合わせ、以下を1枚のカードに収める。

```
[写真]
車名（メーカー + 車種 + グレード）
支払総額（大きく） / 車両本体価格（小さく）
年式 | 走行距離 | 車検 | 修復歴
```

年式・走行距離・車検・修復歴の4点は、**一覧の段階で比較したい情報**であり、
これが無いと詳細ページを1台ずつ開く必要が生じる。年齢層の高い利用者ほど
往復の負担が大きいため、一覧で判断できることの価値が高い。

### 3.2 詳細ページ

既存サービスの定石である**「主要諸元表」**を上部に置く。
現状は項目が縦に長く並ぶだけで、比較しづらい。

```
1. 写真ギャラリー
2. 車名・価格（支払総額 / 本体価格 / 諸費用の内訳）
3. 主要諸元表（年式・走行・車検・修復歴・排気量・ミッション・駆動・ハンドル・color 等）
4. 装備品一覧
5. 店舗からのコメント（既存の販売コメント・店長コメント等）
6. 問い合わせ導線（既存の固定バー）
```

### 3.3 検索条件

データ追加後に絞り込みへ加える候補（優先度順）:
1. 車検（整備付 / 残あり）
2. 修復歴なし
3. 装備品（革シート、サンルーフ等）
4. ハンドル位置

## 4. 実装の優先順位

| # | 内容 | 理由 | 状態 |
|---|---|---|---|
| 1 | 車検の状態（`shaken_status`） | 実データを正しく表現できない唯一の項目。seed投入時に既に破綻している | 完了 |
| 2 | 一覧カードの情報量 | 実装コストが小さく、比較のしやすさに直結する | 完了 |
| 3 | 取引条件（法定整備・保証） | 全掲載車に存在する情報であり、信頼性の訴求になる | 完了 |
| 4 | 詳細ページの主要諸元表 | 既存サービスの定石。慣れた操作感につながる | 完了 |
| 5 | 装備品（マスタ＋中間テーブル） | 項目数が多く工数も大きいため後段。ただし差別化余地も大きい | 未着手 |
| 6 | ハンドル位置・定員・ドア数・燃料等 | 単純なカラム追加。まとめて実施 | 完了 |

### 4.1 実施内容（#4・#6）

詳細ページの車両情報を、単一の一覧から「基本情報／エンジン・駆動／外装・内装／販売条件」の
4グループに分割した。項目数が増えたことで、フラットに並べたままでは目的の情報に
たどり着けなくなるため（既存の中古車サイトが例外なくグループ分けしている理由と同じ）。
値が未登録の項目は行ごと出さず、1項目も残らないグループは見出しごと出さない。

あわせて、公開ページに表示されるのに管理画面に入力欄が無かった項目を追加した。
**修復歴・排気量・車検満了日**を含んでおり、これらが入力できない状態では
掲載情報として成立していなかった（seedデータ経由でしか値を入れられなかった）。

「あり／なし」項目はチェックボックスではなく3択のselectとした。
チェックボックスでは「未設定」と「なし」を区別できず、
未入力の車両がすべて「修復歴なし」として公開されてしまうため。

## 5. 留意点

- **既存データを壊さない**。追加カラムはすべて nullable とし、未入力でも表示が崩れないようにする
- 表示側は「未設定の項目は出さない」を徹底する。空欄や「-」を並べると情報が無いことが強調され、
  かえって不信感につながる
- 管理画面の入力項目が増えるため、**現地クイック登録では引き続き最小項目のみ**とし、
  詳細は後から追記できる現在の設計を維持する
