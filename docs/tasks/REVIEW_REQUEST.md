## 1. どういうプロダクトか

神奈川県川崎市のクラシックJaguar専門店「エムガレージ」（創業30年規模の個人商店）向けの、
**在庫掲載・集客・顧客管理を1つにまとめたWebプラットフォーム**です。

事業上の要点は3つ。

1. **車を売る** — 在庫車両を掲載し、問い合わせにつなげる。グーネット・車選びドットコムにも
   出稿しているが、自社サイトを主戦場にしたい
2. **問い合わせを取りこぼさない** — 電話・LINE・フォーム・来店で入る相談を1箇所に集約する。
   最重要CTAはLINE相談
3. **専門店としての信頼を示す** — Jaguar図鑑・年表・用語ライブラリといった
   コンテンツ資産（130件超）でロングテール検索を取り、「詳しい店」であることを示す

主な購買層は**50〜60代**。「奇抜さより、使い慣れた操作感」を優先し、
一覧・検索まわりはカーセンサー／グーネット／車選びドットコムの作法に意図的に寄せています。

運用者は**店主1人（59歳・非エンジニア）**。管理画面はスマートフォンでの利用を前提にしています
（ガレージで車を撮りながらその場で登録する、という使い方が実際にある）。

**私（発注者の子）はエンジニアではありません。** 開発はすべてAIエージェントに任せており、
コードの妥当性を自分で判断できないことが、このレビューをお願いする最大の理由です。

## 6. レビューしてほしい論点

不安に思っている順です。

### 6-1. 🔴 ライブ編集機能のセキュリティ設計（今回の最重要）

`/admin/live` に公開サイトをiframeで表示し、クリックした箇所をその場で編集できる機能を入れました。
非エンジニアの店主が「項目名から探す」作業を無くすためのものですが、
**公開サイト側に編集用のマーカーを描画する**という性質上、設計を誤ると一般客に露出します。

現在の設計:

| 論点 | 実装 |
| --- | --- |
| 編集モードの判定 | `mg_live_edit` Cookie **かつ** 管理者セッションが有効なときだけ有効（`lib/live-edit/context.ts`） |
| 編集モードでないとき | `<Editable>` はDOMに何も足さない（属性もクラスも増えない） |
| 書き換え可能な範囲 | `lib/live-edit/registry.ts` の許可リストにある「型 × 列」のみ。テーブル名・列名をリクエストから受け取らない |
| 除外した項目 | 公開ステータス・slug・関連付け（クリック1つで公開状態が変わる事故を防ぐため） |
| 保存API | 項目単位の専用API。既存のPATCH（フォーム全体のスキーマ検証前提）とは分離 |
| 監査 | 全書き込みを `audit_logs` に記録 |
| postMessage | 親子とも `event.origin !== window.location.origin` で弾く |

自分で確認できた範囲では、未ログインでAPIは401、Cookieだけでは公開画面に何も出ません。

**聞きたいこと**:
- この設計に穴はありますか。特に **CSRF**（Cookie認証でJSONのPATCHを受けています）と、
  iframe経由のpostMessageの扱いについて
- 「公開サイトのコードに編集用の分岐を埋め込む」というアプローチ自体、
  実務ではどう評価されますか。別системにすべきでしょうか
- `registry.ts` のような許可リスト方式で、将来の追加時に穴が空きにくいでしょうか

### 6-2. 🔴 認可がすべてアプリ層にある（RLSを使っていない）

全テーブルで `enable row level security` はしていますが、**ポリシーを1つも定義していません**。
サーバー側からは常に Service Role Key（RLSをbypassする）でアクセスし、
**認可判定をAPI層のセッション検証に一本化**しています
（判断の経緯は `docs/tasks/ISSUE-002-rls-policies-undefined.md`）。

- 良い点：認可ロジックが1箇所に集まり、SQLとTypeScriptに二重管理が生じない
- 怖い点：**公開ページのクエリが `status = 'published'` や `deleted_at is null` を
  書き忘れた瞬間、非公開・削除済みのデータが公開側に出る**。DB側に最後の砦が無い

確認済みの事実:
- 管理系42ルートすべてに `requireAdminUser` が入っています
  （例外は `DELETE /api/admin/live-edit/session` の1本のみ。編集モードのCookieを消すだけの操作で、
  ログインを要求すると「Cookieだけ残って自力で戻せない」状態が起きうるため意図的に外しています）
- Service Role Key を参照するのは `lib/supabase/admin.ts` と `app/sitemap.ts` の2ファイルのみ
- `createAdminClient` を使う25ファイルのうち24ファイルに `import "server-only"` があります
  （残り1つは `lib/supabase/middleware.ts`。proxy専用のため）

**聞きたいこと**: この体制（1人運用）でRLSを入れないこの判断は妥当でしょうか。
入れるとしたらどこから入れるのが費用対効果が高いですか。
あるいは「公開クエリは必ず特定のヘルパを通す」といった型・Lintでの縛りの方が現実的でしょうか。

### 6-3. 🔴 AIエージェントに実装を任せる進め方そのもの

今回、**4体のエージェントを同時に走らせて**24時間で10コミット・本番反映まで行いました。
人間のレビューは1度も挟んでいません（型チェック・Lint・テスト・ビルドの機械的な検証のみ）。

自分で認識しているリスク:
- AIの指摘・実装が「それらしいが検証されていない」ときに、私には気付けない
- 並列実装は担当ファイルを分けているが、**設計の一貫性**は保証されていない
- コミットメッセージは丁寧だが、それが実装の正しさを意味しない

**聞きたいこと**:
- 実務でAIを使っている立場から見て、この進め方のどこが最も危ういですか
- 人間が1人だけ関われるとしたら、どの工程に入るのが最も効くと思いますか
  （要件定義／設計レビュー／PRレビュー／リリース判断のどこか）

### 6-4. 🟠 同じ不具合を2回出した件（プロセスの問題として）

「車両情報を更新できない」という不具合を、8/15に修正したのに8/17に再発させました。

- 1回目の原因：入れ子になった写真管理UIの `<input required>` が、親フォームの送信を止めていた
- 2回目の原因：**別経路**。`<select>` で「未設定」を選ぶと空文字になり、
  zodの `z.enum([...]).nullable()` を通らない。react-hook-formは検証に失敗すると
  **送信関数を呼ばずに黙って終わる**ため、画面上は「押しても無反応」になる

2回目の修正では、原因を潰すだけでなく
(a) 空文字→nullの変換を18箇所に入れ、(b) 検証で止まったら必ず画面に理由を出し、
(c) フォーム全体を `noValidate` にしてブラウザ検証を無効化しました。回帰テストも13ケース追加しています。

**聞きたいこと**: 「症状は同じだが原因が違う」不具合の再発を防ぐために、
このくらいの規模のプロジェクトで現実的な打ち手は何ですか。
（テスト？型？そもそもフォームライブラリの選定？）

**聞きたいこと**: この手の「気付けない詰まり方」を早期に検知する仕組みとして、
