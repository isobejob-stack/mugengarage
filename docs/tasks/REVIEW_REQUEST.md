## 1. どういうプロダクトか

神奈川県川崎市のクラシックJaguar専門店「エムガレージ」（創業30年規模の個人商店）向けの、
**在庫掲載・集客・顧客管理を1つにまとめたWebプラットフォーム**です。

事業上の要点は3つ。

1. **車を売る** — 在庫車両を掲載し、問い合わせにつなげる。グーネット・車選びドットコムにも
   出稿しているが、自社サイトを主戦場にしたい
2. **問い合わせを取りこぼさない** — 電話・LINE・フォームで入る相談を1箇所に集約する。
   最重要CTAはLINE相談
3. **専門店としての信頼を示す** — Jaguar図鑑・年表・用語ライブラリ・整備実績といった
   コンテンツ資産（100件超）でロングテール検索を取り、「詳しい店」であることを示す

主な購買層は**50〜60代**。したがって「奇抜さより、使い慣れた操作感」を優先しています。
一覧・検索まわりはカーセンサー／グーネット／車選びドットコムの作法に意図的に寄せています。

運用者は**店主1人**（59歳）。管理画面はスマートフォンでの利用を前提にしています
（ガレージで車を撮りながらその場で登録する、という使い方が実際にある）。

## 3. 進め方の特徴（ここが一番見てほしいかも）

**設計ドキュメントを先に書き、そこにIDを振って、コードから参照する**という進め方をしました。

- 機能要件に `FR-INV-009`（車両写真アップロード）のようなIDを振る（**87個**）
- 業務ルールに `BR-DEL-003`（売約済み車両は削除不可）のようなIDを振る（**33個**）
- 実装コードのコメントに、そのコードがどのIDを満たすものかを書く
- 画面は `SCR-PUB-002` のようなIDで管理する

```
docs/requirements/   00_project 〜 06_acceptance_criteria
docs/architecture/   bounded_context / domain_model / event_flow / system_architecture
docs/database/       er_diagram / table_definitions / index_strategy / migration_policy
docs/api/            rest_api / error_response / pagination / authentication
docs/screens/        画面一覧 / 公開UI仕様 / 管理UI仕様 / UIルール
docs/decisions/      ADR
docs/tasks/          ISSUE-001〜006、進捗ステータス
```

`lib/` は境界づけられたコンテキスト単位（inventory / knowledge / content / archive /
crm / engagement / seo / audit / auth / settings）で切っています。

**聞きたいこと**: この「ドキュメント先行＋ID参照」のやり方は、
1人＋AIで2万行を破綻させずに回す方法として妥当だと思いますか。
それとも、この規模ならもっと素朴に進めた方が速かったと思いますか。
（実感としては、AIに文脈を渡す装置としては効いた一方、ドキュメントと実装の
乖離を人手で検知できていないのが不安です）

## 5. レビューしてほしい論点

自分で不安に思っている順です。ここだけでも意見をもらえると助かります。

### 5-1. 🔴 認可がすべてアプリ層にある（RLSを使っていない）

全テーブルで `enable row level security` はしていますが、**ポリシーを1つも定義していません**。
その代わり、サーバー側からは常に Service Role Key（RLSをbypassする）でアクセスし、
**認可判定をAPI層のセッション検証に一本化**しています（`lib/supabase/admin.ts`、
判断の経緯は `docs/tasks/ISSUE-002-rls-policies-undefined.md`）。

- 良い点：認可ロジックが1箇所に集まり、SQLとTypeScriptに二重管理が生じない
- 怖い点：**公開ページのクエリが `status = 'published'` や `deleted_at is null` を
  書き忘れた瞬間、非公開・削除済みのデータが公開側に出る**。
  DB側に最後の砦が無い

管理系43ルートは全てに `requireAdminUser` が入っていることは確認済みですが、
「公開クエリの絞り込み忘れ」を機械的に防ぐ仕組みはありません。

**聞きたいこと**: この規模・この体制（1人運用）で、RLSを入れないこの判断は妥当でしょうか。
入れるとしたらどこから入れるのが費用対効果が高いですか。
あるいは、RLSではなく「公開クエリは必ず特定のヘルパを通す」といった型・Lintでの
縛りの方が現実的でしょうか。

### 5-2. 🔴 テストが実質ほぼ無い

**テストファイル1本・7ケース**だけです（`tests/api/admin/vehicles-id.route.test.ts`）。
論理削除と価格履歴という「壊れると取り返しがつかない」2つのルールだけをカバーしています。

2万行に対して明らかに足りていない自覚はあります。一方で、1人運用でこれから機能追加も
続く中、どこから増やすのが投資対効果が高いか判断できていません。

**聞きたいこと**: この状況でテストを増やすなら、どこから手を付けますか。
（候補：公開クエリの絞り込み条件／Zodスキーマ／APIの認可／E2Eで主要導線1本）

### 5-3. 🟠 商用利用なのにVercel Hobbyプランのまま

Hobbyプランは商用利用不可です（`docs/tasks/ISSUE-003`）。加えてCronが1日1回に制限されるため、
**公開予約の反映が最大約1日遅れる**という機能制約が今出ています。
独自ドメイン（`m-garage.com` 予定）の取得と合わせて対応予定ですが未着手です。

実際、この制約が原因で**約1週間デプロイが全て失敗し続けていた**ことがありました
（Cronを毎時で登録していたためVercelがデプロイごと拒否。ビルドログにも出ず気付きにくかった）。

**聞きたいこと**: この手の「気付けない詰まり方」を早期に検知する仕組みとして、
個人〜小規模で現実的な打ち手は何がありますか。

### 5-4. 🟠 車両写真が1枚も入っていない

在庫21台（公開16台）を掲載していますが、`vehicle_photos` が**0件**です。
中古車サイトとして致命的な状態で、これは店主が写真をアップロードするしかありません。

暫定策として、写真が無い車両の詳細ページは「写真は準備中です／写真をLINEで請求できます」
という導線に変え、**離脱ではなく問い合わせに変換する**作りにしました。

**聞きたいこと**: 初回リリースの判断として、写真が揃うまで公開を待つべきか、
今の状態でも出して運用しながら埋めるべきか。事業判断としてどう考えますか。

### 5-5. 🟡 単一管理者前提の設計

`admin_users.role` カラムはあるものの「将来のマルチユーザー拡張を見据えた予約カラム」で、
権限による分岐は実装していません。今は店主1人なので実害はありませんが、
スタッフが増えたときの移行コストを過小評価していないか気になっています。

### 5-6. 🟡 「取り返しがつく」ことに寄せた設計のコスト

全エンティティに論理削除＋復元UI＋監査ログを入れています。
店主1人が現場で操作する前提なら妥当だと考えましたが、
実装・保守コストに見合っているかは自信がありません。

## 8. 補足：AIエージェントの使い方

役割ごとに人格を定義したサブエージェント（`.claude/agents/`）を用意し、
実装だけでなく**判断**も分担させています。

`engineering-director`（コード品質・業務ルール遵守）／`pdm`（優先順位）／
`business-owner`（事業判断）／`uiux-designer`・`graphic-designer`・
`product-design-manager`（デザイン）／`head-of-jaguar`（Jaguarドメイン知識の監修）／
`frontend-engineer`・`backend-engineer`（実装）

たとえば直近の一覧・検索の作り込みは、`uiux-designer` に
「中古車メディアの作法と比較して劣っている点を事業インパクト順に挙げる」レビューをさせ、
その指摘に沿って実装しています。

**聞きたいこと**: この「AIに役割を持たせて意思決定させる」やり方について、
実務でやっている立場から見て危ういと感じるところはありますか。
（自分では、AIの指摘が“それらしいが検証されていない”ときに
気付けないのが最大のリスクだと思っています）
