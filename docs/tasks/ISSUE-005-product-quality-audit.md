## 2. 🔴 LINE相談のリンク先が仮の値のまま

`lib/site-config.ts` の `LINE_URL` が `https://line.me/`（プレースホルダ）のまま。
この定数は**6ファイル**から参照され、トップ・車両詳細・相談メニュー等、
サイト全体のLINEボタンすべてのリンク先になっている。

現状、相談しようとした見込み客は**LINE社のトップページ**に飛ばされる。

- 01_business_requirements.md でLINE相談は**最重要CTA**と定義されている
- つまり**主要なコンバージョン経路が現在まったく機能していない**
- カテゴリ別プリフィル文言（FR-LINE-002）等、周辺実装は完成済み。**URLを差し替えるだけで全て動く**

> 実装作業は不要。公式LINEアカウントのURLをいただければ1行で反映できる。
> あわせて、`buildLineConsultationUrl` が使う `?text=` プリフィル形式が
> LINE公式仕様どおりかを、実URL確定時に検証する必要がある（コード内にも注記済み）。

## 3. 🔴 検索結果・SNS共有での表示文言（本PRで修正）

`app/layout.tsx` のルート `metadata` が以下だった。

```
title:       "M-GARAGE Platform"
description: "クラシックJaguar専門店エムガレージの在庫・CRM・CMS統合プラットフォーム"
```

- これは**開発側から見たシステム名**であり、顧客向けの文言ではない
- `generateMetadata` を実装しているのは**18ページ中1ページ（車両詳細）のみ**。
  残る17ページはすべて上記を継承しており、Googleの検索結果には
  全ページ同一のタイトルと「CMS統合プラットフォーム」という文言が出ていた
- 同一タイトルの量産はSEO上も不利（重複タイトル）

さらに **OGPが車両詳細以外に未設定**だった。LINEが最重要導線でありながら、
ブログ記事や店舗ページのURLをLINEで送ってもプレビューカードが出ず、
ただのURL文字列として表示されていた。

→ ルートに顧客向けの `title`（`template` 付き）・`description`・`openGraph`・`twitter` を設定。

**追記（対応済み）**: 残り17ページすべてに固有の `title` / `description` / `canonical` / OGP を実装した。
共通ヘルパは `lib/seo/metadata.ts`。

- 一覧・静的ページ（11件）は `buildPageMetadata` による静的 `metadata`
- 詳細ページ（ブログ・図鑑・ライブラリ・整備実績・オーナーズアーカイブの5件）は
  `generateMetadata` で本文から固有の説明文を生成（`excerptFromMarkdown`）
- トップは `title.default` を使い、canonicalのみ明示
- 車両詳細は既存実装が `｜M-GARAGE Platform` をタイトルに直書きしていたため、
  `title.template` と二重になる問題を解消。管理画面でSEOタイトルが指定された場合は
  `absolute` で運用者の文言をそのまま使う

## 5. 🔴 通信断でフォームが固まる（一部修正）

`fetch` を使う **20ファイル中19ファイルが try/catch を持たない**。

通信そのものが失敗する（オフライン・電波断・タイムアウト）と `fetch` は reject し、
送信ハンドラを抜けてしまう。結果として:

1. 送信中フラグを戻す処理に到達せず、**ボタンが「送信中...」のまま永久に固まる**
2. エラーメッセージも出ないため、利用者には何が起きたか分からない
3. 復帰手段が無く、リロード＝入力やり直しになる

とくに影響が大きい2箇所:

- **公開の問い合わせフォーム**（`components/crm/inquiry-form.tsx`）
  スマートフォンからの送信中に電波が切れると、問い合わせが**無言で消える**。
  「問い合わせを取りこぼさない」という事業目的に直撃する
- **現地クイック登録**（`components/inventory/quick-vehicle-register.tsx`）
  屋外のガレージで使う前提の機能であり、通信断が最も起きやすい場面

→ 共通ヘルパ `lib/api/client.ts`（`postJson` / `patchJson` / `deleteJson`）を追加し、
上記2箇所を移行。通信失敗も必ず画面上のメッセージとして返るようにした。

**追記（対応済み）**: 残り全ファイルの移行を完了。`fetch` を直接呼ぶ箇所は
**20ファイル → 1箇所**（写真の一括削除。元から `try/catch` で正しく処理されているため据え置き）。

移行の過程で、応答を一切見ていない箇所も見つかったため併せて修正した。

- `inquiry-status-select.tsx`: 対応ステータスを変更しても応答を確認しておらず、
  保存に失敗しても画面上は新しいステータスのままだった。
  **「対応済みにしたつもりが記録されていない」**状態になりうる。失敗時は表示を戻して理由を出す
- `reminder-toggle.tsx`: 同様。リマインダーは「対応期日を忘れない」ための機能であり、
  完了操作が記録されていない状態は実害が大きい
- `favorite-button.tsx`: 楽観的更新のロールバックが、通信失敗時には実行されていなかった

`lib/api/client.ts` には `sendJson`（新規/編集でメソッドが変わるフォーム用）と、
409などで文言を出し分けたい呼び出し元のために `status` を追加した。

## 6. 🟠 エラー境界が無い（本PRで修正）

`error.tsx` / `global-error.tsx` / `loading.tsx` が**1つも存在しなかった**。

公開ページは全てリクエストごとにDBを読む（`force-dynamic`）ため、
DB障害時に例外が発生する経路は現実に起こりうる。その際、
Next.jsの既定エラー画面がそのまま見込み客に表示されていた。

→ `app/error.tsx` を追加。再試行・トップへ戻る・LINE相談への導線を残し、
障害時にも顧客を取りこぼさない作りにした。エラーIDのみ表示し、例外内容は露出しない。

## 7. 🟡 公開POSTにレート制限が無い

`POST /api/inquiries` は認証不要の公開エンドポイントで、
`customers` テーブルと `inquiries` テーブルに直接書き込む。

- Zodによる入力検証はある（良い）
- 一方で**レート制限・honeypot・CAPTCHA等が一切ない**

小規模店舗のCRMにスパムが流入すると、本物の問い合わせが埋もれる。
これも「取りこぼさない」という目的を損なう。

対策の重さの順:
1. honeypot項目（実装コスト最小・UXへの影響なし）
2. 同一IP/セッションからの連続送信を一定時間制限
3. Cloudflare Turnstile 等の導入（過剰の可能性あり）

なお `await request.json()` も try/catch されておらず、
壊れたJSONを送られると500になる（本来は400が適切）。

## 8. 🟡 ローディング表示が無い

`loading.tsx` が無いため、`force-dynamic` 化した各ページはDB応答待ちのあいだ
**前のページに留まったまま無反応**に見える。
リンクを押しても何も起きないように感じられ、二度押しを誘発する。

各一覧ページにスケルトンを置くと体感速度が明確に改善する。

## 12. 店舗情報・リンクの管理画面化（対応済み）

住所・電話番号・営業時間・LINE URL・掲載媒体リンクが `lib/site-config.ts` に定数として
ハードコードされており、変更のたびに開発とデプロイが必要だった。
とくに `LINE_URL` は仮の値のまま全ページのCTAに使われ、**開発者を介さないと
最重要導線を直せない**状態になっていた。BR-DATA-003 の「ハードコードしない」方針を
店舗プロフィールにも適用し、DB管理へ移行した。

| 追加物 | 内容 |
|---|---|
| `supabase/migrations/20260808150000_create_site_settings_table.sql` | 単一行の設定テーブル |
| `lib/settings/schema.ts` / `queries.ts` | Zod検証・取得・更新 |
| `app/api/admin/site-settings/route.ts` | GET/PATCH（認証＋監査ログ） |
| `app/admin/(protected)/site-settings/page.tsx` | 管理画面「店舗情報・リンク設定」 |

設計上のポイント:

- **単一行を構造的に保証**。`id text primary key default 'singleton' check (id = 'singleton')` とし、
  行が増えて「どれが正か分からない」状態をDB側で防ぐ
- **掲載媒体リンクは JSONB 配列**。媒体は今後増減しうるため、列を増やさず順序付きで持つ。
  管理画面から行の追加・削除ができる
- **未設定は NULL、表示側は出さない**。空欄や誤情報を顧客に見せない
- **LINE URLが未設定のあいだはLINEボタン自体を表示しない**。仮URLへ飛ばすより害が小さい
- **取得失敗時は空設定にフォールバック**。フッターは全ページから参照されるため、
  マイグレーション未適用やDB障害でもサイト全体を落とさない（`app/sitemap.ts` と同じ方針）

### 併せて修正した既存の不具合

`audit_logs.target_id` が `uuid not null` だったため、`'singleton'` を対象とする監査ログの
INSERTが型違反で失敗する状態だった。`recordAuditLog` は insert のエラーを見ていないため、
画面上は成功したように見えてログだけ残らない**サイレント失敗**になる
（`20260807120000` で `restore` がCHECK制約に無く同じ壊れ方をしたのと同種）。
「監査対象は必ずUUIDを持つ」という前提が成り立たなくなったため、`target_id` を `text` に広げた。

## 12.1 トップページのヒーロー写真（対応済み）

トップページの第一印象が「黒い箱＋テキスト」で、クラシックJaguar専門店にとって
最も情緒に訴える資産である車と店の写真が使われていなかった。

一方で、画像の保管先は `vehicle-photos`（車両に紐づく写真）しか無く、
**店舗外観やガレージの様子といった「店そのものを伝える写真」を置く場所が無かった**。

→ サイト素材用のStorageバケット `site-assets` を追加し、
管理画面「店舗情報・リンク設定」からヒーロー写真をアップロードできるようにした。

- `site_settings.hero_image_path` に保管先を保持
- 設定されていれば**全幅の写真ヒーロー**、未設定なら従来の文字ベースにフォールバック
- 写真は差し替えのたびに明るさが変わるため、**文字の可読性を写真任せにしない**。
  下方向へ濃くなるスクリムを重ね、白文字とのコントラストを常に確保する（WCAG 1.4.3）
- ヒーロー画像はLCPそのものなので `priority` を付与
- 差し替え時は「アップロード → DB更新 → 旧ファイル削除」の順で行い、
  DB更新に失敗した場合はアップロード済みファイルを取り消す（孤児ファイルを残さない）

なお、チャット等で共有された画像をリポジトリのファイルとして保存することはできないため、
**写真そのものは管理画面からアップロードしてもらう必要がある**。

### ⚠️ マイグレーションの手動適用が必要

この環境ではマイグレーションが自動適用されない。**SupabaseのSQL Editorで
以下の2つを順に実行すること。**

1. `20260808150000_create_site_settings_table.sql`
2. `20260808160000_create_site_assets_bucket.sql`（1に依存）
未適用のあいだは設定が空として扱われ、住所やLINEボタンが表示されない（サイトは正常に動く）。

適用後、管理画面 **設定 > 店舗情報・リンク** から以下を入力する。

- 住所（郵便番号含む）・電話番号・営業時間・定休日・創業年・代表者名・アクセス
- LINEのURL ← **これを入れた時点で全ページのCTAが復活する**
- 掲載媒体リンク（グーネット / 車選びドットコム / Instagram / Facebook）

住所・電話・営業時間を入力すると、`/about` の `AutoDealer` 構造化データにも
`address` / `telephone` / `openingHours` が自動的に含まれ、
Googleのローカル検索やマップでの表示に効く。

## 12. 推奨する着手順

1. **LINE_URLの差し替え**（作業0.5h／発注者の情報待ち）— 効果が最大
2. **各ページの `generateMetadata`**（17ページ）— コンテンツ資産の回収
3. **残り17フォームのAPIクライアント移行** — 堅牢性
4. **honeypotによるスパム対策** — 低コスト
5. **`loading.tsx` の追加** — 体感速度
6. **構造化データの展開**（`Article` / `DefinedTerm` / `BreadcrumbList`）
7. **ヒーロー写真の導入** — 素材選定が必要
