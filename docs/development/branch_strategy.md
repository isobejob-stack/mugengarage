# branch_strategy.md — ブランチ戦略

## 1. Purpose（目的）

GitHubリポジトリ上でのブランチ運用ルールを定義する。開発者はClaude Code（AI）が中心であり、人間のレビュアーが常時いない前提（00_project.md 8章）のため、過度に複雑なブランチ運用は避け、Vercelの自動デプロイの仕組みと相性の良いシンプルな運用とする。

## 2. Scope（対象範囲）

GitHubリポジトリのブランチ運用、Vercelとの連携（Preview Deployments）を対象とする。

## 3. 基本方針

- `main` ブランチ＝本番環境。`main` へのpushはVercelにより自動的に本番サイトへ反映される（system_architecture.md 5章）
- 過剰なブランチ運用（例：Git Flowのような複数階層）は本プロジェクトの規模には不要と判断し、採用しない（過剰最適化の回避、00_project.md 12章）

## 4. ブランチの種類

| ブランチ    | 用途                                                 |
| ----------- | ---------------------------------------------------- |
| `main`      | 本番。常にデプロイ可能な状態を保つ                   |
| `feature/*` | 新機能・大きめの変更（例：`feature/vehicle-search`） |
| `fix/*`     | 不具合修正（例：`fix/price-history-bug`）            |

## 5. 運用ルール

- ある程度まとまった変更（新しいドメインの実装、DBスキーマ変更を伴う変更等）は `feature/*` ブランチで作業し、Vercelの Preview Deployment（ブランチごとに自動生成される確認用URL）で動作確認してから `main` にマージする
- 小さな修正（誤字修正、軽微なスタイル調整等）は `main` への直接コミットを許容する（レビュー体制が薄い前提のため、過剰な手続きより「作り直しが効く」ことを重視する）
- `main` は常にビルドが通る状態を保つ。ビルドが失敗する変更は反映しない

## 6. Vercel Preview Deploymentsの活用

- `feature/*` ブランチをGitHubにpushすると、Vercelが自動的にそのブランチ専用の確認用URLを発行する
- 発注者（非エンジニア）に変更内容を確認してもらう際は、本番環境ではなくこのPreview URLを共有する（本番データに影響を与えず確認できる）

## 7. 大きな変更（DBスキーマ変更等）の注意点

- migration_policy.md に従い、マイグレーションを伴う変更は特に慎重に扱う
- 本番データが既に入っている状態でのスキーマ変更は、必ずバックアップ確認後に実施する（migration_policy.md 8章）

## 8. Acceptance Criteria（本ドキュメントの受け入れ基準）

- [ ] `main` ブランチが常にデプロイ可能な状態を保つ運用ルールになっている
- [ ] Vercel Preview Deploymentsの活用方法が明記されている
- [ ] 非エンジニアの発注者にも変更確認の仕組み（Preview URL）が用意されている
