# testing_strategy.md — テスト戦略

## 1. Purpose（目的）

品質保証の方針を定義する。人間の専任QA担当者がいない前提のため、特に「間違えると事業的に致命的な業務ルール」を優先してテストで担保し、それ以外は過剰投資しない（実現可能性・保守性を優先、00_project.md 6章）。

## 2. Scope（対象範囲）

自動テスト（ユニット・結合）と、リリース前の手動確認チェックリストを対象とする。

## 3. テスト方針の優先順位

すべての機能を同じ密度でテストするのではなく、**業務ルール（BR-ID）に関わる箇所を最優先**でテストする。

| 優先度 | 対象                                        | 理由                                                       |
| ------ | ------------------------------------------- | ---------------------------------------------------------- |
| 最優先 | BR-DEL-001〜003（論理削除・売約済車両保護） | 誤ってデータが消えると復旧不能、事業への影響が大きい       |
| 最優先 | BR-HIST-001（価格履歴の追記）               | 履歴が壊れるとオーナーズアーカイブ・信頼性に関わる         |
| 高     | BR-DOM-001〜004（ドメイン独立性）           | Knowledge系がVehicleに依存しないことはビジネスゴールの根幹 |
| 高     | BR-URL-001〜002（URL永続化・301）           | SEO評価の毀損は事業目標に直結する                          |
| 中     | 検索・絞り込み（FR-SRCH-001）               | ユーザー体験に直結するが、誤りがあっても致命的ではない     |
| 中     | CRM・問い合わせ（FR-CRM, FR-INQ）           | 顧客対応に影響するため中程度の優先度                       |
| 低     | AI補助機能（FR-AI-001〜004）                | あくまで「提案」であり、誤りがあっても人間が最終確認する   |

## 4. 自動テストの種類

| 種類           | 対象                                                                                         | ツール想定                                                                |
| -------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| ユニットテスト | 価格変更ロジック、論理削除ロジック、ステータス遷移バリデーション等、業務ルールに直結する関数 | Vitest または Jest                                                        |
| APIテスト      | rest_api.md で定義した主要エンドポイント（特に管理系のCUD操作）                              | Vitest + テスト用DB（Supabaseのテスト用プロジェクト or ローカルPostgres） |
| E2Eテスト      | 最重要シナリオのみ（例：車両登録→公開→検索結果に表示、問い合わせ送信→管理画面に反映）        | Playwright（最小限、全画面を網羅しない）                                  |

## 5. 手動確認チェックリスト（リリース前）

新機能リリース時・大きな変更時は、以下を最低限手動確認する。

- [ ] 論理削除したデータが公開ページ・検索結果に表示されないこと
- [ ] 論理削除したデータが管理画面上では復元可能であること
- [ ] 価格を変更した際、price_historiesに正しく履歴が追加されること（上書きされていないこと）
- [ ] 売約済みに変更した車両が、削除ではなくステータス変更として扱われ、オーナーズアーカイブに反映されること
- [ ] Slugを変更した際、301リダイレクトが自動作成され、旧URLでアクセスしても新URLに転送されること
- [ ] 図鑑・年表・ライブラリの新規項目が、対応する在庫車両がなくても公開できること
- [ ] スマホ実機（またはブラウザのスマホ表示モード）で、主要画面のタップ操作・文字サイズに問題がないこと

## 6. テストデータ

- 本番データとは別に、開発・テスト用のSupabaseプロジェクト（または同一プロジェクト内のテスト用スキーマ）を用意し、実データに影響を与えずに確認できるようにする
- テストデータには実在の顧客情報を使用しない（個人情報保護の観点、03_non_functional_requirements.md 9章）

## 7. Acceptance Criteria（本ドキュメントの受け入れ基準）

- [ ] テストの優先順位が、04_business_rules.mdのBR-IDの重要度と整合している
- [ ] 自動テストと手動確認の役割分担が明確になっている
- [ ] 本番データを汚染しないテストデータ運用ルールが明記されている
