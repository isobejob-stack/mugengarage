# deployment.md — デプロイ運用

## 1. Purpose（目的）

system_architecture.md 5章で定義したデプロイフローを、実際の運用手順・環境管理のレベルまで具体化する。

## 2. Scope（対象範囲）

環境（本番／プレビュー）の管理、ドメイン設定、環境変数管理、障害時のロールバック手順を対象とする。

## 3. 環境構成

| 環境                  | 用途                                                     | URL                                                        |
| --------------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| Production（本番）    | 一般公開されるサイト                                     | 独自ドメイン（例：`m-garage.jp` 等、取得済みのものを設定） |
| Preview（確認用）     | `feature/*` ブランチごとに自動生成（branch_strategy.md） | `*.vercel.app` の自動発行URL                               |
| Local（ローカル開発） | Claude Codeによる実装・動作確認時                        | `localhost:3000`                                           |

## 4. 初期セットアップ手順（概要）

1. GitHubリポジトリを作成する
2. Supabaseプロジェクトを作成し、`docs/database/migration_policy.md` の順序でテーブルを作成する
3. Vercelアカウントを作成し、GitHubリポジトリと連携する
4. Vercelの環境変数にSupabaseの接続情報（URL・APIキー）を設定する
5. 独自ドメインを取得済みの場合はVercelに設定する（未取得の場合は `*.vercel.app` の無料ドメインで開始し、後から独自ドメインを追加できる）
6. 管理者アカウント（`admin_users`）を初期作成する

**注**：発注者自身がこれらの手順を実施する必要はなく、Claude Codeによる実装時に案内・代行する想定とする（00_project.md 8章、ノーコード運用の前提）。

## 5. 通常運用時のデプロイフロー

system_architecture.md 5章の通り、`main` ブランチへのpushで自動デプロイされる。運用者（発注者）が意識する操作は発生しない。

## 6. 障害・不具合発生時の対応

| 状況                                   | 対応                                                                             |
| -------------------------------------- | -------------------------------------------------------------------------------- |
| デプロイ後にサイトが正常に表示されない | Vercelの管理画面から直前の正常なデプロイへ即座にロールバック（Vercelの標準機能） |
| データベースの不整合が疑われる         | Supabaseの自動バックアップから復旧を検討する（migration_policy.md 8章）          |
| 管理画面にログインできない             | Supabase Authの管理コンソールからアカウント状態を確認する                        |

## 7. 監視・通知（初期リリースの範囲）

- Vercel・Supabaseそれぞれの標準ダッシュボードで稼働状況を確認できる（追加の監視ツール導入は初期リリースでは不要と判断、過剰投資の回避）
- ビルド失敗時はVercelからのメール通知を利用する

## 8. ドメイン・DNS

- 独自ドメインを使用する場合、DNS設定（Aレコード／CNAME）をVercelの指示に従って設定する
- HTTPS証明書はVercelが自動発行・自動更新する（発注者側での証明書管理は不要）

## 8.1 VercelのHobby（無料）プランに関する重要な注意（2026-08-05追記）

Vercel公式ドキュメント（[Hobby Plan](https://vercel.com/docs/plans/hobby), 2026-06-16更新版）に以下の明記がある。

> As stated in the fair use guidelines, the Hobby plan restricts users to **non-commercial, personal use only**.

エムガレージは実店舗の商用サイトであるため、本番公開後もHobby（無料）プランを使い続けることはVercelの利用規約に反する。**独自ドメイン（`.com`等）を設定するだけではこの問題は解決しない**（プランとドメインは別軸の話であり、独自ドメインをHobbyプランのプロジェクトに設定しても規約違反は解消されない）。本番公開に進む際は、次の2つをセットで行う必要がある。

1. Vercel **Proプランへのアップグレード**（商用利用として正式な状態にする。14日間の無料トライアルあり）
2. 独自ドメイン（`.com`等）の取得・設定（`*.vercel.app`は信頼性・ブランディングの観点でも本番URLとして不適切）

開発・確認段階（Preview環境、社内的な動作確認）では `*.vercel.app` のままでも実務上問題になりにくいが、一般ユーザーへの本番公開時点までにはこの2点の対応を完了させること。詳細は [docs/tasks/ISSUE-003](../tasks/ISSUE-003-production-domain-and-plan-upgrade.md) を参照。

## 8.2 検証済みコミット（署名）とデプロイのブロック（2026-08-16追記）

Vercelのチーム設定 Security & Privacy に「検証済みコミットを要求する（Require verified commits）」がある。有効にすると、**GitHubで「Verified」と表示されないコミットのビルドがブロックされる**。チーム全体の設定だが、説明文の通りプロジェクト側（Project → Settings → Git）で上書きできる。

同じ画面のすぐ上にある「保護されたGitスコープ」はエンタープライズプラン限定（アップグレードボタンが付く）だが、**検証済みコミットの要求はそれとは別機能で、無料プランでも利用できる**。GitHub側も、コミット署名と「Verified」バッジは全プラン（Freeを含む・プライベートリポジトリ可）で無料で使える。GPG・SSH・S/MIMEのいずれでも署名できる。したがって「無料プランだから署名できない」という制約は存在しない。

なお、GitHubのブランチ保護ルール「Require signed commits」はプライベートリポジトリでは有料プランが必要だが、Vercelはコミットの検証状態を自前で見るため、そちらを設定する必要はない。

### 実測結果（2026-08-16、本リポジトリで確認）

「GitHub API経由で作ったコミットはGitHubが署名するので常にVerifiedになる」という一般論があるが、**本リポジトリの現在の構成では成立しなかった**。実際にコミットを作ってコミットオブジェクトを検査した結果は次の通り。

| 経路                                            | 実測                                            |
| ----------------------------------------------- | ----------------------------------------------- |
| `main` の既存コミット（`6ad46f0` 等）           | 署名なし（`gpgsig` ヘッダーが存在しない）       |
| Claude Code実行環境からの `git push`            | SSH署名が付く（環境が管理する鍵で自動署名）     |
| GitHub API（Git Data API／`push_files`）        | **署名なし**                                    |
| GitHub API（Contents API／ファイル単位の更新）  | **署名なし**                                    |

つまりAPI経由に切り替えても署名は付かない。実行環境の署名鍵は `/tmp/code-sign` という環境管理のプログラムが握っており、リポジトリ側からは差し替えられない。またSSH署名が付いていても、**その公開鍵がGitHubアカウントの Settings → SSH and GPG keys → Signing keys に登録されていなければ「Verified」にはならない**。登録状況は実行環境からは確認できない（`api.github.com` への到達がネットワークポリシーで塞がれているため）。

### 現時点ではブロックされていない（実測）

上記の調査中、署名がVerifiedである保証のないコミットをブランチにpushしてプレビューデプロイを実行させたところ、**ブロックされずに成功した**（PR #3、デプロイ `42zryXVDbngv1Ud7J1yjMcmKoe4h` がReady）。したがって、この設定は現在このプロジェクトのデプロイを妨げていない。チーム設定のトグルが「無効」であることとも整合する。

**結論として、今の時点で対応は不要**である。デプロイが失敗した場合は、まずVercelのビルドログで実際のエラーを確認すること。署名とは無関係の原因（ビルドエラー、環境変数の不足など）である可能性が高い。

### 将来この設定を有効にする場合の選択肢

チーム設定またはプロジェクト設定で要求を有効にした場合、リポジトリ側の工夫だけでは対応できず、**いずれの案も発注者による1回の操作が必要**になる。ただし変更のたびに操作が必要になる案はない。

1. **Vercelのプロジェクト設定で上書きをオフにする**（Project → Settings → Git）。確実で、以後の運用コストがゼロ。署名によるブロックをやめる判断になる。
2. **実行環境の署名鍵をGitHubアカウントのSigning keysに登録する**。登録すれば `git push` されたコミットがVerifiedになる。ただし環境が管理する鍵であり、セッションをまたいで同じ鍵が使われる保証は確認できていないため、鍵が変わると再登録が必要になる可能性がある。
3. **`main` へのマージをGitHubのマージボタン（Squash and merge）で行う**。Web UI経由のマージコミットはGitHubが署名するため `main` はVerifiedに保たれる想定だが、本調査では未検証。またブランチのプレビューデプロイは対象外となる。

なお、着手前にVercelのビルドログで実際のエラーがコミット署名によるものかを確認すること。チーム設定のトグル自体は「無効」であり、ブロックされているならプロジェクト側の上書きが原因になる。
