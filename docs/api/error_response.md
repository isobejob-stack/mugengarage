# error_response.md — エラーレスポンス仕様

## 1. Purpose（目的）

全APIエンドポイントで統一されたエラーレスポンス形式を定義する。エラー処理をエンドポイントごとにバラバラに実装させず、Claude Codeが機械的に統一実装できるようにする（00_project.md 12章「密結合」を避ける設計原則にも寄与）。

## 2. Scope（対象範囲）

rest_api.mdで定義する全APIエンドポイントのエラーレスポンスを対象とする。

## 3. 共通エラーレスポンス形式

すべてのエラーは以下のJSON形式で返す。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "価格は0以上の整数で入力してください",
    "field": "price",
    "details": null
  }
}
```

| フィールド | 説明                                                                         |
| ---------- | ---------------------------------------------------------------------------- |
| `code`     | エラー種別を表す機械可読なコード（3章参照）                                  |
| `message`  | 管理画面・公開画面にそのまま表示できる、日本語の人間向けメッセージ           |
| `field`    | バリデーションエラーの場合、対象のカラム／入力項目名（対象外の場合は`null`） |
| `details`  | 追加情報が必要な場合のみ使用（通常は`null`）                                 |

複数項目のバリデーションエラーが同時に発生した場合は、`errors` 配列形式で複数返す：

```json
{
  "errors": [
    {
      "code": "VALIDATION_ERROR",
      "message": "車両名は必須です",
      "field": "model_id"
    },
    {
      "code": "VALIDATION_ERROR",
      "message": "価格は0以上で入力してください",
      "field": "price"
    }
  ]
}
```

## 4. HTTPステータスコードとエラーコードの対応

| HTTPステータス | エラーコード         | 意味                   | 発生例                                                                       |
| -------------- | -------------------- | ---------------------- | ---------------------------------------------------------------------------- |
| 400            | VALIDATION_ERROR     | 入力値が不正           | 必須項目未入力、型不一致、範囲外の値                                         |
| 401            | UNAUTHORIZED         | 未認証                 | 管理系APIに未ログインでアクセス                                              |
| 403            | FORBIDDEN            | 権限不足               | 将来の権限拡張後、権限外の操作を試みた場合                                   |
| 404            | NOT_FOUND            | 対象データが存在しない | 存在しないIDの車両詳細取得、論理削除済みデータへのアクセス                   |
| 409            | CONFLICT             | データの競合           | 同一Slugの重複登録、同一VINの重複登録                                        |
| 422            | UNPROCESSABLE_ENTITY | 業務ルール違反         | 売約済み車両を物理削除しようとした等、BR-IDに反する操作                      |
| 429            | RATE_LIMITED         | リクエスト過多         | 短時間の連続お気に入り登録等、想定外の連続リクエスト                         |
| 500            | INTERNAL_ERROR       | サーバー内部エラー     | 想定外の例外。詳細はログにのみ記録し、ユーザーには一般的なメッセージのみ返す |

## 5. 業務ルール違反時のエラーメッセージ方針

BR-IDに違反する操作が試みられた場合、開発者向けの技術的なメッセージではなく、管理者（非エンジニア）が理解できる日本語メッセージを返す。

| 違反ルール                           | エラーメッセージ例                                                         |
| ------------------------------------ | -------------------------------------------------------------------------- |
| BR-DEL-003（売約済み車両の削除禁止） | 「売約済みの車両は削除できません。オーナーズアーカイブとして保持されます」 |
| BR-HIST-001（価格履歴の上書き禁止）  | （UIレベルで価格の直接編集のみを許可し、履歴改ざんの入口自体を作らない）   |
| BR-URL-002（Slug変更時の301設定）    | （エラーではなく、Slug変更時に自動でリダイレクトが作成される旨をUIに表示） |

## 6. フロントエンド側での表示方針

- `VALIDATION_ERROR`：該当する入力項目のすぐ下に赤字でメッセージを表示する
- `UNAUTHORIZED`：ログイン画面に自動遷移する
- `NOT_FOUND`（公開ページ）：カスタム404ページを表示する（車両が売却済み・削除済みの場合、関連する車両へのリンクを提示するなど、離脱を防ぐ工夫を行う）
- `INTERNAL_ERROR`：「時間をおいて再度お試しください。改善しない場合はサイト管理者にご連絡ください」等の一般的なメッセージを表示し、内部エラー詳細は表示しない（セキュリティ上の理由）

## 7. Acceptance Criteria（本ドキュメントの受け入れ基準）

- [ ] 全APIエンドポイントが本ドキュメントのエラー形式に統一されている
- [ ] HTTPステータスコードとエラーコードの対応が過不足なく定義されている
- [ ] 業務ルール（BR-ID）違反時に、非エンジニアが理解できる日本語メッセージが定義されている
- [ ] セキュリティ上、内部エラーの詳細情報がユーザーに露出しない設計になっている
