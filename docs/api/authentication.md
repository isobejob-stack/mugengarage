# authentication.md — 認証仕様

## 1. Purpose（目的）

管理画面（Admin UI）へのアクセス制御、および公開サイト（Public Website）側で必要となる最小限の識別の仕組みを定義する。03_non_functional_requirements.md 9章（セキュリティ要件）「管理画面へのアクセスは認証必須とする」を実装レベルに落とし込む。

## 2. Scope（対象範囲）

Admin UIの認証・認可、公開サイト側の匿名セッション管理（お気に入り機能用）を対象とする。将来のマルチユーザー・権限拡張（FR-ADM-002）の土台となる設計とする。

## 3. 認証方式

- **Admin UI**：Supabase Auth（メールアドレス＋パスワード方式）を用いる。管理者アカウントは `admin_users` テーブルで管理し、Supabase Authの `auth.users` と1:1で連携する（table_definitions.md 12.1）
- **Public Website**：一般ユーザー向けの会員登録・ログイン機能は初期リリースでは実装しない（01_business_requirements.md 8章、将来対応）。お気に入り機能は、ブラウザに保存する匿名セッションID（`session_id`）で識別する（table_definitions.md 9.1）

## 4. アクセス制御ルール

| 対象                                                      | ルール                                                                                                                                                    |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/admin/*`（管理画面の全ページ）                          | 認証必須。未ログインの場合はログイン画面にリダイレクトする。例外はログイン画面自身とパスワード再設定の申請画面（`/admin/forgot-password`）のみ（7.1参照） |
| 管理系API（車両登録・編集・削除、顧客情報の閲覧・編集等） | すべてSupabase Authのセッション検証を必須とする                                                                                                           |
| 公開系API（車両一覧・検索・詳細取得、記事閲覧等）         | 認証不要。誰でもアクセス可能                                                                                                                              |
| お気に入り登録・解除API                                   | 認証不要だが、匿名セッションIDをリクエストに含める                                                                                                        |
| 問い合わせフォーム送信API                                 | 認証不要（一般ユーザーからの送信のため）                                                                                                                  |

## 5. 権限モデル（初期リリース）

- 初期リリースでは管理者アカウントは少数（1〜数名）を想定し、単一ロール（`admin`）のみとする（03_non_functional_requirements.md 3章）
- `admin_users.role` カラムを予約しておき、将来的な権限細分化（例：閲覧のみ権限、CRM閲覧不可権限等）に備える（FR-ADM-002）
- 初期リリースでは全管理者が全機能にアクセスできる（権限による機能制限は行わない）

## 6. セッション管理

- Admin UIのセッションはSupabase Authが発行するJWT（アクセストークン）を利用する
- トークンの有効期限・リフレッシュはSupabase Authの標準機構に従う
- ブラウザを閉じても一定期間はログイン状態を保持する（スマホでの日常運用の利便性を優先、03_non_functional_requirements.md 8章）

## 7. パスワード・アカウント管理

- 管理者アカウントの**新規作成**は、初期リリースでは開発者（Claude Code経由の初期セットアップ）またはSupabase管理コンソールから行う
- **パスワードリセット**は、管理画面内の再設定フローで完結できる（発注者と確認のうえ実装、2026-08-16）

### 7.1 パスワード再設定フロー

| 手順 | 実装                                  | 内容                                                                                                 |
| ---- | ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1    | `/admin/forgot-password`              | メールアドレスを入力し、`resetPasswordForEmail` で再設定メールを送信する。未ログインで到達できる     |
| 2    | メール内リンク → `/api/auth/callback` | Supabase Authが付与する `?code=` をセッションに交換する（PKCEフロー）。失敗時は理由付きで手順1へ戻す |
| 3    | `/admin/reset-password`               | `updateUser` で新しいパスワードを設定する。完了後はそのまま管理画面へ入る                            |

**設定上の前提**：手順2の遷移先はSupabase Authの許可リストに載っている必要がある。Supabaseダッシュボードの Authentication > URL Configuration で、`Redirect URLs` に本番とプレビューの `/api/auth/callback` を登録する（未登録だとメール内のリンクが `Site URL` に飛ばされ、再設定画面に到達できない）。Vercelのプレビューはデプロイごとにホスト名が変わるため、ワイルドカード（例：`https://mugengarage-git-*.vercel.app/api/auth/callback`）で登録する。

照合はURL全体に対するパターンマッチであるため、`resetPasswordForEmail` に渡す `redirectTo` には**クエリ文字列を付けない**。遷移先は `/api/auth/callback` 側の既定値（`/admin/reset-password`）に持たせ、許可リストの登録値と完全に同じ文字列を渡す。`?next=` を付けると登録値と一致せず `Site URL` に飛ばされる可能性がある。

- パスワードは12文字以上を必須とする（顧客情報を扱うため、Supabase既定の6文字より強い下限を課す。03_non_functional_requirements.md 9章）
- 手順2の遷移先（`next`）は自サイト内の絶対パスに限定し、オープンリダイレクトを防ぐ
- 手順1の結果表示はメールアドレスの登録有無で変えない（アカウント存在の推測を防ぐ）
- 管理画面内からの自己アカウント管理機能（ログイン中のパスワード変更等）は、現時点では未実装とする

### 7.2 メールが受け取れない場合の復旧手段

登録メールアドレスが受信できない、管理者アカウント自体が存在しない等で上記フローが使えない場合は、`supabase/reset-admin-password.sql` の手順をSupabaseのSQL Editorで実行する。認証を無効化することなくパスワードを再設定できる。

## 8. セキュリティ上の注意点

- 全通信をHTTPS化する（03_non_functional_requirements.md 9章）
- 管理系APIは、リクエストごとに認証トークンの検証を行う（フロントエンドの画面制御だけに頼らない）
- 顧客情報（CRM）を含む管理系APIは、認証済みリクエストであっても、想定外の大量取得（全顧客データの一括ダウンロード等）を防ぐレート制限を検討する

## 9. Acceptance Criteria（本ドキュメントの受け入れ基準）

- [ ] Admin UIの全ページ・全管理系APIが認証必須であることが明記されている
- [ ] 公開系API（車両閲覧・検索等）が認証不要であることが明記されている
- [ ] 匿名セッション（お気に入り機能）の識別方式が定義されている
- [ ] 将来の権限拡張（FR-ADM-002）を見据えた予約設計になっている
