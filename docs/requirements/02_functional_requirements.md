# 02_functional_requirements.md — 機能要件

## 1. Purpose（目的）

01_business_requirements.md で定義したビジネス要件を、「システムが提供すべき具体的な機能」に分解する。各機能にはFR-ID（Functional Requirement ID）を付与し、以降のDB設計・API設計・画面設計から参照可能にする。

## 2. Scope（対象範囲）

初期リリースに含める機能をドメインごとに列挙する。将来対応項目（01の8章）はここには含めない。

### 掲載情報の網羅性（2026-08-13 再定義）

中古車情報サイト（カーセンサー・グーネット・車選びドットコム）で標準的に掲載される項目に対し、
当システムが持てていなかった項目を洗い出して追加した。詳細な経緯と項目定義は
docs/tasks/ISSUE-006-vehicle-listing-requirements.md を参照。

判定の根拠は、発注者から共有されたグーネットの実掲載データ15台分（一次情報）とした。
3サイトへは開発環境から到達できないため、サイトを直接参照した項目の網羅ではない。

**車検の扱い（重要）**

車検は「車検整備付」「満了日あり」「なし」の3状態を持つ。日付のみで表現してはならない。
実在庫の大半が「車検整備付」であり、日付欄しか持たない設計では表現できないため。
満了日が年月までしか判明していない場合は「◯年◯月」とだけ表示し、日を推測で補完しない
（購入判断に関わる情報を誤って表示することになるため）。

**取引条件**

法定整備・保証（有無／期間／距離）・リサイクル料金を持つ。
掲載データ全件に記載があり、購入総額と信頼性の判断に直結するため。

**ハンドル位置**

輸入車であるクラシックJaguarでは購入判断を大きく左右するため、国産中心のサイトより
重要度が高い項目として扱う。

**未設定項目の扱い**

追加項目はすべて任意入力とし、**未設定の項目は公開サイトに表示しない**。
空欄や「-」を並べると情報が無いことが強調され、かえって不信感につながるため。

**表示文言の一元化**

車検・走行距離・修復歴等の表示文言は lib/inventory/display.ts に集約する。
同じ項目を画面ごとに組み立てると「車検残」「車検満了」「車検」のような表記揺れが生まれるため。
走行距離は中古車サイトの慣例に合わせ、1万km以上を「◯.◯万km」と表記する。

**未実装（優先度順）**: 装備品（マスタ＋中間テーブル）、詳細ページの主要諸元表。

| ID          | 機能             | 詳細                                                                                                                                                                       |

| FR-SRCH-001 | 絞り込み検索     | 車種・車両本体価格・年式・走行距離・ミッション・シリーズ・世代・グレード・排気量・駆動方式・外装色の複合条件で絞り込む（条件の見直し経緯は下記「絞り込み条件の方針」参照） |

| FR-SRCH-003 | 検索条件の保持   | ページ遷移後も検索条件を保持する（ブラウザバック等）                                                                                                                       |

### 絞り込み条件の方針（2026-08-13 見直し）

当初は保有カラムをほぼすべて条件として並べていたが、実運用に照らして以下を削除した。
条件を増やすほど探しやすくなるわけではなく、**選ばれない条件が並ぶこと自体が
フォームを煩雑にし、目的の条件にたどり着く妨げになる**という判断による。

| 削除した条件                                         | 理由                                                                                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| メーカー                                             | 取り扱いがジャガー・デイムラーに限られる専門店では選択肢として機能しない                                                   |
| 車検                                                 | 掲載情報の大半が「車検整備付」で満了日を持たず、日付で絞ると大半が除外される（実在庫15台中13台）。実質機能しない条件だった |
| 馬力・オーナー数・内装色・シート素材・屋内保管・タグ | 発注者判断により削除。データは保持しており、車両詳細での表示・管理画面での入力には引き続き使う                             |

**入力形式の方針**: 価格・年式・走行距離・排気量はプルダウンとする。
中古車情報サイト（カーセンサー・グーネット・車選びドットコム）はいずれも
「万円」単位のプルダウンを採用しており、購買層が慣れた操作である。
また円単位の数値入力は桁を数える負担が大きく、スマートフォンでは特に不利になる。

**表示ラベルの方針**: 範囲指定は「ラベル1つ＋下限〜上限」に統一する。
ラベル側に「（下限・円）」「（上限）」のような但し書きを持たせると項目ごとに表記が揺れ、
折り返しも発生するため。

## 補足: 公開予約の反映間隔について（2026-08-13 追記）

FR-INV-007 / FR-BLOG-004 の公開予約は、定期実行（Vercel Cron Jobs）で実現している。

**現状の制約**: VercelのHobby（無料）プランは1日1回より高頻度の定期実行を許可していない。
毎時実行を設定していたところ、デプロイ自体が拒否され、
**公開予約に限らずサイトの更新が一切反映されない状態**が発生した（docs/tasks/ISSUE-005）。

このため現在は1日1回（毎日09:00 JST）に設定しており、
**公開予約の反映が最大約1日遅れる**。

Proプランへのアップグレード（docs/tasks/ISSUE-003。商用利用のため元々必須）の完了後、
毎時実行に戻すことで解消する。

> 教訓として、ホスティングのプラン制約は「使える機能の上限」ではなく
> **デプロイの成否そのものに影響しうる**。定期実行やビルド時間に関わる設定を変える際は、
> 契約プランの制限を先に確認すること。
