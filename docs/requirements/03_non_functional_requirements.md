# 03\_non\_functional\_requirements.md — 非機能要件

## 1\. Purpose（目的）

01・02で定義したビジネス要件・機能要件を「どのレベルの品質・性能・安全性で実現するか」を数値・基準として定義する。ここでの数値は、以降のインフラ選定（architecture/）・DB設計・実装の判断基準となる。

## 2\. Scope（対象範囲）

性能、可用性、スケーラビリティ、SEO、アクセシビリティ、セキュリティ、データ保全（バックアップ・履歴・監査ログ）、運用コストを対象とする。インフラの具体的な選定・契約は architecture/ 配下のADRで別途決定する。

## 3\. 想定規模（Scale Assumptions）

| 項目                         | 想定値                                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 常時在庫台数                 | 10〜50台程度                                                                                                                |
| オーナーズアーカイブ累積台数 | 長期運用（10年以上）で数百台規模まで蓄積される想定                                                                          |
| 同時アクセスユーザー数       | 小〜中規模（専門店サイトとして、通常時は数十セッション程度、SNS流入等のスパイク時でも数百セッション程度を許容できればよい） |
| 管理者アカウント数           | 少数（1〜数名）                                                                                                             |
| 写真枚数                     | 車両1台あたり実質50枚程度、上限は設けない                                                                                   |

**方針**：大規模トラフィックへの過剰最適化は行わない（実現可能性・保守性を優先）。ただし将来的な台数増加・トラフィック増加に対して、作り直しが必要にならない設計とする。

## 4\. パフォーマンス要件

- 主要な公開ページ（トップ、車両詳細、図鑑、ブログ）は、モバイル回線でも初回表示（LCP）を意識した高速表示を実現する
- 画像は自動的に最適化（圧縮・適切なフォーマット変換・遅延読み込み）される
- 検索・絞り込みは体感的な待ち時間を感じさせない応答速度とする
- 管理画面の操作（保存・公開切り替え等）は即座にフィードバックが返る

## 5\. 可用性（Availability）

- 通常営業に支障が出ない可用性を確保する（大規模専門インフラは不要。マネージドサービスの標準SLAで足りる規模と位置づける）
- 障害発生時も、公開サイトの閲覧・車両情報の表示は極力継続できる構成が望ましい

## 6\. スケーラビリティ

- 在庫台数10〜50台規模、将来のアーカイブ蓄積を前提に、台数増加によってDB設計・画面表示の作り直しが発生しない構造とする
- 将来のCSV／外部API連携（01の8章）に備え、データ構造を疎結合に保つ

## 7\. SEO要件

- 全ページでTitle/Description/OGP/Canonical/構造化データ（Schema.org JSON-LD）を出力可能にする
- URLは意味のあるSlugで構成し、変更時は301リダイレクトで旧URLの評価を維持する
- サイトマップ・robots.txtを自動生成・自動更新する
- Core Web Vitals（表示速度・インタラクティブ性・レイアウト安定性）を意識した実装とする

## 8\. アクセシビリティ・UI要件

- 高齢ユーザー（40〜70代のメイン顧客層、55歳の非エンジニア管理者）に配慮し、文字サイズ・ボタンサイズを大きめにする
- タップ・クリック操作の対象領域を十分に確保する
- コントラスト比等、基本的なアクセシビリティ基準に配慮する
- スマホファーストで設計し、PC表示はスマホ表示の拡張として扱う

## 9\. セキュリティ要件

- 管理画面へのアクセスは認証必須とする
- 顧客情報（CRM）は個人情報として適切に保護し、不要な第三者アクセスを防ぐ
- 通信は常時HTTPS化する
- 画像・動画等のアップロードファイルは想定外の形式・サイズを制限する
- 定期的なバックアップを取得する

## 10\. データ保全要件

- 論理削除：車両・記事・図鑑・整備実績等、すべての主要データは物理削除せず論理削除で扱う
- 価格履歴：車両価格の変更はすべて履歴として保持する
- 変更履歴（監査ログ）：管理画面上の主要な変更操作（誰が・いつ・何を変更したか）を記録する
- バックアップ：データベース・メディアファイルは定期的にバックアップを取得し、復旧可能な状態を保つ

## 11\. 運用・コスト要件

- サーバー管理・運用コストを最小化する（インフラの選定は「特に希望なし・おまかせで低コスト・低運用負荷優先」という前提で、architecture/ フェーズにてマネージド型のホスティング・データベースサービスを中心に検討する）
- 管理者はコードを書かず、ノーコードで日常運用（車両登録・記事投稿・ステータス変更等）が完結できること
- 障害対応・アップデート対応において、専門のインフラエンジニアが常駐しなくても運用できる構成とする

## 12\. 長期運用要件

- 10年以上の運用を想定し、特定ベンダー・特定技術への過度な依存（ロックイン）を避ける設計とする
- ドキュメント・設計資産を体系的に残し、将来担当AI・担当者が入れ替わっても継続開発できる状態を維持する

## 13\. Acceptance Criteria（本ドキュメントの受け入れ基準）

- \[ ] 想定規模（3章）が、DB設計・インフラ選定の判断基準として具体的な数値で示されている
- \[ ] 論理削除・価格履歴・監査ログ等、01・02で定義した業務ルールと矛盾する非機能要件が存在しない
- \[ ] インフラの具体的な製品・サービス名の決定は本ドキュメントでは行わず、architecture/ 配下のADRに委譲されている
