# 06_acceptance_criteria.md — 要件定義フェーズ 受け入れ基準

## 1. Purpose（目的）

00〜05で作成した要件定義一式（requirements/）が、次工程（architecture/）へ進める品質に達しているかを判定するための、フェーズ全体の受け入れ基準を定義する。各ドキュメント個別のAcceptance Criteriaは各ファイル末尾に記載済みであり、本ドキュメントはそれらを横断的に確認するための最終チェックリストとして機能する。

## 2. Scope（対象範囲）

`docs/requirements/` 配下の以下6ファイルを対象とする。

- 00_project.md
- 01_business_requirements.md
- 02_functional_requirements.md
- 03_non_functional_requirements.md
- 04_business_rules.md
- 05_glossary.md

## 3. ドキュメント間の一貫性チェック

| #   | チェック項目                                                                             | 状態 |
| --- | ---------------------------------------------------------------------------------------- | ---- |
| 1   | 00のプロダクトゴール（4章）が、01のビジネスゴール（3章）と矛盾なく対応している           | ☑    |
| 2   | 01の全ビジネス機能要件（4.1〜4.19）が、02のFR-IDとして過不足なく機能分解されている       | ☑    |
| 3   | 02の各FRが、04の業務ルール（BR-ID）に反していない                                        | ☑    |
| 4   | 03の非機能要件（想定規模・パフォーマンス等）が、02の機能要件の実現可能性と矛盾していない | ☑    |
| 5   | 04に集約された業務ルールが、00〜03に記載された業務ルールを漏れなく反映している           | ☑    |
| 6   | 05の用語定義が、00〜04内で使われている専門用語・独自定義語をすべてカバーしている         | ☑    |
| 7   | 01の「将来対応・スコープ外」（8章）の項目が、02の機能要件（FR-ID）に誤って含まれていない | ☑    |

## 4. 主要な業務ルールが機能要件に正しく反映されているかの確認

| 業務ルール（BR-ID）                  | 対応するFR-ID・確認内容                                                                                   |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| BR-DEL-001（論理削除）               | FR-INV-003, FR-BLOG-001, FR-ENC-001, FR-TL-001, FR-LIB-001, FR-MNT-001 が「削除（論理）」と明記されている |
| BR-DEL-003（売約済車両は削除しない） | FR-INV-004（ステータス変更）とFR-OWN-001（自動アーカイブ）が整合している                                  |
| BR-DOM-001〜004（ドメイン独立性）    | FR-ENC-003（在庫非依存の独立公開）で担保されている                                                        |
| BR-HIST-001（価格履歴）              | FR-INV-006（価格変更・履歴保持）で担保されている                                                          |
| BR-URL-001, 002（URL永続化・301）    | FR-SEO-003, FR-SEO-004 で担保されている                                                                   |
| BR-AI-001, 002（AIは提案のみ）       | FR-AI-001〜004 の注記で担保されている                                                                     |
| BR-SCOPE-002（LINE APIは実装しない） | FR-LINE-003（公式LINEへの遷移のみ）で担保されている                                                       |

**運用ルール**：要件が曖昧なまま実装を進めてはならない（BR-SCOPE-003）。今後の設計・実装フェーズで判断に迷う点が出た場合は、推測で進めずここに追記し、`docs/tasks/` にIssueとして記録する。

## 6. 次フェーズ（architecture/）へ進む条件

- [ ] 00〜05の全ファイルについて、発注者（人間）が内容を確認し、事実誤認・認識齟齬がないことを確認済みである
- [ ] 3章・4章の一貫性チェックにすべて問題がないことを確認済みである
- [ ] 未決事項（5章）が「実装を止めるレベルの重大な曖昧さ」を含んでいない（軽微な詳細は architecture/ 以降で詰めてよい）
- [ ] `docs/requirements/` 配下に00〜06の7ファイルが揃っている

すべて満たされた場合、次工程 `docs/architecture/`（system_architecture.md, domain_model.md, bounded_context.md, event_flow.md）に進む。

## 7. Acceptance Criteria（本ドキュメント自体の受け入れ基準）

- [ ] 00〜05の各ドキュメントのAcceptance Criteriaが本ドキュメントで横断的に参照・確認できる
- [ ] 次フェーズへ進む条件（6章）が明確なチェックリストとして機能する
- [ ] 本ドキュメントは要件定義フェーズの「完了宣言」としての役割を持つ
