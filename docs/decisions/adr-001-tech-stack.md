# ADR-001: 技術スタックの選定

## Status（状態）

Accepted（採用）

## Context（背景・課題）

M-GARAGE Platformは以下の制約・要件を満たす技術構成を選定する必要がある（詳細は `docs/requirements/` 参照）。

- 運用者は非エンジニア（55歳、スマホ中心）であり、サーバー管理・コード記述をさせられない（BR原則、03章）
- サーバー管理コスト・運用コストを最小化したい（発注者の明確な希望：「特にない・おまかせで低コスト・低運用負荷優先」）
- SEOを非常に重視する（03_non_functional_requirements.md 7章）
- 在庫台数10〜50台規模、長期運用（10年以上）を想定し、過剰な技術選定を避ける（00_project.md 12章）
- 車両情報・CRM・問い合わせ・価格履歴・監査ログ等、複雑な業務ロジックを持つデータを扱うため、単純な静的サイト（HTMLだけの公開サイト）や既製のノーコードHP作成サービス（Wix, STUDIO等）では機能要件（在庫管理・CRM・グレード別テンプレート等）を満たせない
- 発注者はインフラ知識がなく「GitHubで公開するイメージ」程度の理解である

## Decision（決定）

以下の技術スタックを採用する。

| レイヤー                   | 採用技術                   | 理由                                                                                                                                                          |
| -------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| フロントエンド／サイト生成 | **Next.js**（React）       | SSR/SSGによりSEOに強い。表示速度が速い。管理画面（Admin UI）も同一プロジェクト内に構築できる                                                                  |
| ホスティング／デプロイ     | **Vercel**                 | GitHubリポジトリに変更をpushすると自動でビルド・公開される。サーバー契約・管理が不要。無料〜低価格帯のプランで本プロジェクトの規模を十分カバーできる          |
| データベース／バックエンド | **Supabase**（PostgreSQL） | 車両・CRM・問い合わせ・価格履歴等の構造化データを保持する。管理コンソールがあり、緊急時は非エンジニアでも中身を確認できる。認証機能・ストレージ機能を標準搭載 |
| 画像・動画ストレージ       | **Supabase Storage**       | 車両写真（1台あたり実質50枚程度）・動画URLの保管先。Vercel/Next.jsとの連携が容易                                                                              |
| ソースコード管理           | **GitHub**                 | コードの保管・変更履歴管理。Vercelとの自動連携により「pushするだけで公開」を実現する                                                                          |

## Consequences（この決定によって生じること）

**メリット**

- サーバー管理・インフラ運用の作業がゼロになる（BR/NFRの「運用コスト最小化」要件を満たす）
- Next.jsの標準機能でSEO要件（Title/Description/OGP/構造化データ/サイトマップ等）をコードレベルで実装できる
- 無料枠〜低コストで開始でき、将来の台数増加時も段階的にプランアップグレードするだけで対応可能（作り直し不要）
- GitHub × Vercelの組み合わせは業界標準的であり、将来別のAI・エンジニアが引き継いでもドキュメント・情報が豊富

**留意点・トレードオフ**

- 発注者自身がインフラの詳細（GitHub操作、Vercel/Supabaseの管理画面）に触れる場面は基本的に発生しない設計とするが、初期セットアップ（アカウント作成等）は必要になる
- Vercel・Supabaseはどちらも米国発のサービスであり、為替変動により将来的な価格が変動する可能性がある（ただし今回の規模では無料〜低価格帯に収まる見込み）
- 特定ベンダーへの依存を完全にゼロにはできないが、Next.js（フレームワーク）・PostgreSQL（データベース標準規格）はオープンな技術のため、将来的に他のホスティング・DBサービスへの移行は可能（ロックインは限定的）

## Alternatives Considered（検討した代替案）

| 案                                        | 不採用の理由                                                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Wix / STUDIO 等のノーコードHP作成サービス | 在庫管理・CRM・価格履歴・グレード別テンプレート等の複雑な業務ロジックを実装できない                                                |
| 静的サイト（HTML直書き＋GitHub Pages）    | 管理画面・データベース・検索機能・CRM等の動的機能を実現できない                                                                    |
| WordPress＋レンタルサーバー               | サーバー管理・セキュリティアップデート対応が発生し「運用コスト最小化」の要件に反する。プラグイン依存が長期運用のリスクになりやすい |
| 自前でVPS/クラウドサーバーを構築          | サーバー管理・保守が必要になり、非エンジニアの運用前提と矛盾する                                                                   |
